officelens

officelens is an MIT-licensed, Bun-based auditor for DOCX and PPTX. It reads the OOXML part XML directly and reports findings as text, JSON, or SARIF 2.1.0, so a CI job can fail on error-severity issues. Documents are read locally and are never uploaded.

Existing accessibility checkers do not cover Office formats

PDF has veraPDF and PAC, EPUB has DAISY ACE, and HTML has axe-core and Pa11y. For .docx and .pptx there is no equivalent offline, scriptable auditor, so officelens fills that gap.

Microsoft Accessibility Checker

Windows, macOS, and web only. No CLI, no JSON, and no presence on a Linux CI runner. Microsoft's own documentation tells teams to run it plus a manual review because it has blind spots.

Accessr

Covers .docx only. No CLI and no JSON, so it cannot sit in a pipeline or gate a pull request.

Schema validators

ooxml-cli, xarsh/ooxml-validator, and openxml-audit check schema and well-formedness only, with no WCAG semantics.

ez-a

A roughly zero-star Python GUI limited to PPTX alt text. No batch mode and nothing to script against.

officelens

Open source, offline, cross-platform, and scriptable. The CLI and the browser playground run the same rules, and both produce machine-readable output for CI.

What officelens checks

officelens parses the OOXML package and checks its XML directly. It runs offline, and the same bytes always produce the same issues.

Deterministic rules

The rules are plain functions, so the same bytes always produce the same issues in the same order and results do not drift between runs.

JSON and SARIF

Emit machine-readable JSON for a pipeline, or SARIF 2.1.0 for GitHub code scanning annotations.

CI exit codes

Exit 1 when an error-severity issue is found, 2 with no arguments, and 0 otherwise.

Offline by default

The CLI makes no network requests and sends no telemetry. Documents stay on the machine, and the browser playground never uploads a file.

CLI and library

Audit batches from the shell, or call audit() directly from TypeScript.

DOCX and PPTX

Checks the structural WCAG failures that block assistive technology in DOCX and PPTX files.

How it works

The package is opened directly and the XML is read. No rendering engine is involved.

  1. 01

    Open the package

    Unzip the OOXML container with fflate and index its parts and relationship graphs.

  2. 02

    Resolve the entry point

    Follow the relationships to the main document part or the presentation part.

  3. 03

    Parse the XML

    fast-xml-parser reads it with attributes enabled — structure and content, never a render.

  4. 04

    Run the rules

    Deterministic rule functions emit Issue[], then a text report, JSON, or SARIF is written.

The rules

Static checks mapped to the WCAG success criteria they most directly support.

DOCX
Code Severity WCAG Check

DOCX-HEAD-002 warning 1.3.1 Body text but no headings at all
DOCX-HEAD-003 warning 1.3.1 Heading levels skip (for example H1 → H3)
DOCX-LANG-004 warning 3.1.1 No document language (w:lang)
DOCX-TBL-005 error 1.3.1 Table whose first row is not a header (w:tblHeader)
DOCX-LINK-006 warning 2.4.4 Hyperlink whose visible text is a raw URL

Code Severity WCAG Check
PPTX-ALT-001 error 1.1.1 Picture or shape (a:cNvPr) without descr

Install

officelens runs on Bun.

# One-line install (installs the `officelens` binary)
curl -fsSL https://raw.githubusercontent.com/srivtx/officelens/main/install.sh | sh

# Or run once, without installing
bunx github:srivtx/officelens report.docx

# Install globally
bun add -g github:srivtx/officelens
officelens report.docx

# Add to a project as a dev dependency
bun add -d github:srivtx/officelens

officelens is not published to npm. Install it with the one-line script, or run it without installing. Fixtures are built in-repo as real OOXML zips with bun run make-fixtures, so the tests exercise the same package parsing path as production files.

CLI and library

Audit from the shell or call the same rule engine from TypeScript.

Command line

# Audit one or more documents (human-readable)
officelens report.docx deck.pptx

# Machine-readable JSON for a pipeline
officelens report.docx --json

# Just the summary line
officelens report.docx --quiet

# Emit SARIF for GitHub code scanning
officelens report.docx --sarif officelens.sarif

Exit code is 1 when any error-severity issue is found, 0 otherwise, and 2 when called with no arguments.

Library

import { audit } from "officelens";

const result = audit(bytes, "report.docx");
// { file, kind: "docx", issues, counts: { error, warning, info } }

Also exported: formatJson, formatText, openOoxml, auditDocx, auditPptx, toSarif, and writeSarif.

SARIF and code scanning

Emit a SARIF 2.1.0 report and let GitHub code scanning annotate the pull request.

permissions:
  security-events: write

steps:
  - name: Accessibility audit (SARIF)
    run: officelens docs/*.docx docs/*.pptx --sarif officelens.sarif

  - name: Upload SARIF
    if: always()
    uses: github/codeql-action/upload-sarif@v3
    with:
      sarif_file: officelens.sarif

Failing the build

--fail-on sets the severity that fails the build: error (default), warning, info, or none. The report is written even when the audit exits non-zero, so the upload step still runs.

Limitations

Static analysis only

officelens does static XML analysis: it reads the parts directly rather than rendering them. Not every WCAG success criterion is machine-checkable, so it covers the structural, high-signal failures that block assistive technology. Spreadsheets (.xlsx) are not covered yet.

FAQ

Are my documents uploaded anywhere?

No. The CLI has no network code, and the playground runs the same bundled rules entirely in your browser tab. No file, or any part of one, is transmitted.

Does it need Word, PowerPoint, or a JVM?

No. officelens opens the OOXML zip and parses its XML directly. There is no Office installation, no headless renderer, and no Java runtime.

Can it fix the documents, or only report them?

It audits and reports; it does not modify your files. That keeps it safe to run in CI over a repository of source documents.

Does it cover spreadsheets?

Not yet. The current rule set targets DOCX and PPTX. .xlsx support is out of scope for now.

Can I gate a pull request on it?

Yes. Use the exit codes for a simple gate, or emit SARIF and upload it with github/codeql-action/upload-sarif so findings appear as code-scanning annotations.

Is it really deterministic?

Yes. The rules are plain deterministic functions, so the same bytes always produce the same issues in the same order.

Audit a file in your browser

Drop a .docx or .pptx file, or run one of the bundled sample files. The audit runs in your browser with the same rules as the CLI, and files are read locally without being uploaded.
